# Interview Review Rubric

Use this rubric when scoring each interview answer and deciding what deserves a question card.

## Dimensions

- correctness: whether the answer is technically true, with formulas and definitions stated in the right direction.
- depth: whether the answer explains mechanism, tradeoff, limitation, and implementation detail rather than only naming concepts.
- structure: whether the answer starts with the direct point, then expands cleanly.
- evidence: whether the answer gives project facts, metrics, code paths, experiment settings, or observed rollout behavior.
- recovery: whether the candidate handles follow-up pressure, uncertainty, and corrections without becoming vague.
- coding clarity: whether the candidate states the invariant, writes a compact template, handles boundaries, and gives complexity.
- interviewer signal: what the interviewer was trying to verify, doubt, or pressure-test.

## Scoring

- strong: correct, structured, evidence-backed, and follow-up ready.
- passable: core direction is right, but one or two details are thin or disorganized.
- risky: interviewer can reasonably doubt the candidate's depth, ownership, or correctness.
- fail-risk: a basic concept is wrong, the answer contradicts itself, or a simple code task becomes unstable.

## Signals To Preserve

- repeated follow-ups on one topic: likely a depth or correctness concern.
- requests for checkpoint, baseline, metric, or reward details: experimental-rigor concern.
- "why not X" questions: tradeoff and design-principle concern.
- interviewer correcting the candidate: high-priority remediation item.
- simple algorithm question causing hesitation: coding baseline risk even if final code passes.
